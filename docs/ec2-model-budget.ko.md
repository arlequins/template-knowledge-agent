# 월 100달러 이하 EC2 모델 및 파인튜닝 예산

언어: [English](ec2-model-budget.md) | **한국어** |
[日本語](ec2-model-budget.ja.md)

이 문서는 애플리케이션 데이터베이스가 이미 존재할 때 AWS에서 월 100달러
미만으로 무엇을 운영할 수 있는지에 관한 제한된 계획 질문에 답한다. 아래
금액은 특정 시점의 가격 스냅샷이며 견적서가 아니다.

## 전제 조건

- 리전: 아시아 태평양(도쿄), `ap-northeast-1`.
- 가격 기준일: 2026-08-25 AWS 공개 Price List, Linux On-Demand, 공유
  테넌시.
- 한 달은 730 인스턴스 시간으로 계산한다.
- 요청에 따라 RDS 비용은 제외한다.
- 세금, 인터넷/NAT 전송, 로드 밸런서, S3, CloudWatch, 스냅샷, 퍼블릭
  IPv4, T 계열 인스턴스의 추가 CPU 크레딧은 제외한다.
- gp3 스토리지는 기본 제공 IOPS와 처리량만 사용한다고 가정한다.
- 중지한 EC2 인스턴스에는 컴퓨팅 비용이 발생하지 않지만 연결된 EBS에는
  계속 비용이 발생한다.

배포 전에는 반드시 [AWS Price List API](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/using-the-aws-price-list-bulk-api-fetching-price-list-files-manually.html)와
[EBS 가격 페이지](https://aws.amazon.com/ebs/pricing/)에서 계산을 갱신한다.

## 초기 출시 목표: 실용적인 일반 대화

첫 릴리스부터 일반 사용자가 쓸 수 있는 대화형 에이전트처럼 동작해야 하며,
프로젝트 전용 파인튜닝을 기다리면 안 된다. 항상 사용 가능한 기본 추론 경로에는
**Bedrock On-Demand**를 사용하고, 저비용 일반 대화 모델의 첫 후보로 Amazon
Nova 2 Lite를 평가한다. provider adapter 경계를 유지하여 파생 저장소가 동일한
replay suite를 통과한 다른 Bedrock, Claude, Gemini, OpenAI, 로컬 모델로 바꿀 수
있게 한다. Bedrock On-Demand는 예약 용량 없이 확장되고 처리 token에 따라
과금되지만 quota는 모델과 리전별로 다르다.
[Nova On-Demand 안내](https://docs.aws.amazon.com/nova/latest/nova2-userguide/on-demand-inference.html)와
[Nova 2 Lite model card](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-amazon-nova-2-lite.html)를
참고한다.

다음은 용량 보장이 아닌 초기 계획 기준이다.

- 등록 사용자 100명, 일간 활성 사용자 20–30명, 일반적인 가벼운 사용에서 동시
  대화 최대 5개;
- 동시 접속 목표를 넘는 짧은 burst는 대기열로 처리하고, 조용히 실패하지 말고
  명확한 혼잡·재시도 메시지를 표시;
- streaming 텍스트 응답, 다중 turn history, Markdown 표시, 답변 복사, 재생성,
  생성 취소;
- 영어·일본어·한국어 acceptance 대화를 각각 측정하고 언어 품질을 추정하지 않음;
- 긴 대화 하나가 지연과 token 예산 전체를 소비하지 않도록 history와 검색
  context를 제한;
- 사용자·workspace별 rate limit, 일간 token 및 비용 경보.

근거 필요성에 따라 요청을 다음처럼 라우팅한다.

1. 일반 대화는 간결한 행동·안전 prompt와 함께 선택한 foundation model로 직접
   보낸다.
2. 저장소, Fumadocs, React, Drizzle 등 승인된 기술 질문에는 검색한 source chunk와
   인용을 추가한다.
3. 최신 공지, 판매, 업무 기록은 허용 목록에 있는 읽기 전용 live capability를
   호출한다.
4. 근거가 없거나 권한이 없는 질문에는 답을 만들지 말고 제한 사항을 명시한다.

출시 전에는 다중 turn 일반 대화 세트, 공개 pilot corpus, 거절 사례, 동시 사용자
5명 부하 테스트를 최소한 replay한다. 첫 token 시간, 전체 응답 지연, token 사용량,
오류율, 반복 문장, 근거 없는 주장, 인용 정확성을 측정한다. 이 baseline이 동작한
뒤 검토된 실패 사례에서 검색·prompt·routing으로 해결할 수 없는 반복 행동 문제가
확인될 때만 파인튜닝을 시작한다.

## 계획 A: 소형 CPU 모델 상시 운영과 간헐적 파인튜닝

Spot 가격에 의존하지 않으면서 월 예산 안에서 계속 접근 가능한 유일한
셀프 호스팅 구성이다.

| 월간 항목 | 계산 | 비용 |
| --- | ---: | ---: |
| `t4g.large` 서비스 | 730 × $0.0864 | $63.07 |
| 서비스 gp3 | 40 GB × $0.096 | $3.84 |
| `g4dn.xlarge` 파인튜닝 실행기 | 30시간 × $0.7100 | $21.30 |
| 파인튜닝 gp3 | 30 GB × $0.096 | $2.88 |
| **소계** |  | **$91.09** |
| 미할당 한도 | $100 − $91.09 | **$8.91** |

CPU 추론에는 4비트로 양자화한 1.5B–3B instruct 모델을 사용한다. 8 GiB에는
런타임, KV 캐시, 검색 컨텍스트, 운영체제가 모두 들어가야 하므로 전체 프로세스의
엄격한 한도로 취급한다. 등록 사용자 약 100명을 지원하려면 트래픽이 가볍고
동시 요청을 의도적으로 대기열에 넣어야 한다. 운영 준비를 선언하기 전에 첫 토큰
응답 시간과 동시 요청을 벤치마크한다.

30 GPU 시간은 체크포인트를 사용하는 짧은 1.5B/3B QLoRA 작업과 평가에
적합하다. T4 16 GB에서 7B/9B 작업을 하려면 매우 짧은 시퀀스, 작은 배치,
gradient checkpointing, CPU offload가 필요할 수 있으므로 기본 권장안이 아니다.
파인튜닝은 서빙과 분리하고, 별도의 held-out 품질·안전 게이트를 모두 통과한
후에만 승격한다.

## 계획 B: 예약된 GPU 시간에 Ornith 1.5 9B 사용

`ornith-ai/Ornith-1.5-9B`는 9B dense 모델이다. Mac 전용
`Ornith-1.5-9B-MLX-4bit` 아티팩트는 NVIDIA CUDA 런타임에 직접 로드할 수
없다. EC2에서는 CUDA QLoRA용 라이선스가 확인된 Hugging Face 원본 가중치나
추론용 호환 GGUF/양자화본으로 시작하고 동일한 평가 스위트를 다시 실행한다.

| 월간 항목 | 계산 | 비용 |
| --- | ---: | ---: |
| `g6.xlarge` | 75시간 × $1.1672 | $87.54 |
| gp3 | 80 GB × $0.096 | $7.68 |
| **소계** |  | **$95.22** |
| 미할당 한도 | $100 − $95.22 | **$4.78** |

75시간은 하루 평균 약 2.5시간이다. 이 시간 동안 예약된 QLoRA/평가와 대화형
테스트를 할 수 있지만 24시간 서비스는 아니다. 24 GB L4는 이 저비용 후보 중
9B 실험에 가장 현실적이다. 다만 호스트 RAM 16 GiB는 여전히 빠듯하므로 작은
데이터셋, 제한된 시퀀스 길이, gradient checkpointing, 재개 가능한
체크포인트를 사용하고 실제 최대 메모리를 측정한다. 작업이 끝나면 인스턴스를
중지한다.

Spot을 사용하면 GPU 시간을 늘릴 수 있지만 가격과 용량을 예산으로 보장할 수
없다. 체크포인트를 영구 저장하고
[2분 전 중단 알림](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-instance-termination-notices.html)을
처리한다.

## 파인튜닝 시간에 따라 달라지는 것

학습 시간은 처리 용량 예산이지 품질 점수가 아니다. GPU 시간이 늘어나면 더 많은
승인 예제를 처리하거나, 여러 후보를 평가하거나, 더 긴 시퀀스를 사용할 수 있다.
반대로 동일한 작은 데이터셋을 더 많은 epoch 동안 반복하면 암기, 문장 반복,
근거 없는 주장, 기존 능력의 회귀가 늘어날 수 있다. 근거에 없는 최신 사실을 새로
만들어 주지도 않는다. 최신 공지, 판매 내역, 저장소 변경은 RAG나 읽기 전용
실시간 도구로 제공해야 한다.

| 후보 1회당 GPU 시간 | 합리적으로 달라질 수 있는 것 | 증명할 수 있는 범위 |
| --- | --- | --- |
| 30분 이하 | CUDA 구성, 데이터셋 형식, 토큰 위치, 체크포인트, 단일 종단간 smoke case 확인 | 파이프라인이 실행된다는 것뿐이며 승격 근거로는 부족함 |
| 30분–2시간 | 검토된 소형 데이터셋으로 작은 LoRA/QLoRA 후보 1개 학습, 짧은 held-out replay | 파일럿 신호일 뿐 광범위한 행동 개선은 아님 |
| 2–8시간 | 승인 예제나 시퀀스 예산 확대, 일부 learning rate/rank 후보 비교, 인용·반복·언어·거절 검사 강화 | 분리된 test set과 앱 전체 replay가 통과할 때만 신뢰할 수 있는 후보 |
| 8–24시간 | 여러 seed나 후보, 더 넓은 회귀 테스트, 지연·비용 측정 | 비교 신뢰도는 올라가지만 답변 품질을 보장하지는 않음 |
| 24시간 초과 | 더 큰 데이터셋·모델, 넓은 hyperparameter 탐색, 반복적인 강건성 검사 | 수익 체감 구간일 수 있으므로 추가 비용 전에 검색·데이터 품질·모델 적합성을 먼저 조사 |

전체 실행 시간에는 데이터 내보내기, 모델 로딩, 평가, 보고서 생성, 체크포인트
업로드도 포함된다. 예약한 인스턴스 시간을 모두 optimizer 학습 시간으로 간주하면
안 된다. 실행 비교를 위해 최소한 데이터셋 버전, base model, adapter 설정,
GPU 종류, 학습 step, 처리 토큰 수, validation loss, held-out 결과, 실제 경과
시간, 최대 메모리를 기록한다.

### 스케줄이 월 비용에 미치는 영향

월간 GPU 컴퓨팅 비용은 대략 다음과 같다.

```text
월 GPU 비용 = 시간당 가격 × 1회 실행 시간 × 월 실행 횟수
```

이 도쿄 가격 스냅샷에서는 다음과 같다.

| 스케줄 예시 | 월 GPU 시간 | 컴퓨팅 비용 | 현실적인 용도 |
| --- | ---: | ---: | --- |
| 월 4회, 2시간 `g4dn.xlarge` | 8 | $5.68 | 파이프라인 및 소형 모델 파일럿 검사 |
| 매일 1시간 `g4dn.xlarge` | 30 | $21.30 | 계획 A에서 배정한 파인튜닝 시간 |
| 월 4회, 4시간 `g6.xlarge` | 16 | $18.68 | 9B 후보 학습과 보호된 평가 |
| 매일 2.5시간 `g6.xlarge` | 75 | $87.54 | 계획 B의 전체 GPU 창이며 EBS 포함 총액은 $95.22 |

표의 시간은 상한 예시이지 권장 최소 시간이 아니다. 새롭게 출처 승인을 받은
예제가 충분할 때만 파인튜닝을 시작한다. 그렇지 않으면 예약 시간을 검색 평가에
사용하거나 실행 자체를 건너뛴다. 매일 평가하더라도 새 adapter를 만들 필요는 없다.
승격은 평가보다 드물어야 하며, 안전·지연·비용 회귀 없이 현재 배포본을 명확히
능가할 때만 수행한다.

### 시간 예산과 관계없이 유지할 통제

- 의미가 비슷한 바꿔쓰기까지 포함하여 train, validation, test set을 분리한다.
- test set으로 hyperparameter를 선택하지 않는다.
- validation 품질이 떨어지거나 반복이 늘면 조기 중단한다.
- 직전 학습 step뿐 아니라 현재 base model과 배포 중인 adapter를 모두 비교한다.
- 승격된 adapter가 활성화됐다고 선언하기 전에 서빙 프로세스를 다시 로드하고
  전체 RAG 답변을 replay한다.
- 버전이 있는 rollback 대상을 보존하며, 비용을 많이 쓴 학습이라도 게이트에
  실패하면 거부한다.

## 권장 서비스 구성

약 100명이 가볍고 간헐적으로 요청하는 서비스라면 기존 애플리케이션 컴퓨팅과
RDS에 **Bedrock On-Demand**를 사용해 24시간 추론을 제공하고, 정확한 오픈
모델이 측정 가능한 우위를 보일 때만 EC2 GPU를 간헐적으로 사용한다. 도쿄 리전의
On-Demand GPU를 월 100달러 이하로 24시간 운영할 수 있는 구성은 없다.

도쿄 가격 견적이 아닌 규모 예시로, AWS 비용 연구는 월 22,000건의 Nova Micro
요청(요청당 입력 800, 출력 60 token)을 추론 약 $0.80, 샘플 파인튜닝 1회를
$8.00로 계산했다. 실제 배포일에는 정확한 모델 지원, 커스터마이징 지원, 가격,
리전 가용성을 확인해야 한다.
[AWS Bedrock 비용 연구](https://aws.amazon.com/blogs/machine-learning/cost-efficient-custom-text-to-sql-using-amazon-nova-micro-and-amazon-bedrock-on-demand-inference/)와
[Bedrock 가격](https://aws.amazon.com/bedrock/pricing/)을 참고한다.

실무 적용 순서는 다음과 같다.

1. 가중치를 변경하지 않고 매일 검색·프롬프트·라우팅 평가를 실행한다.
2. 출처 검토를 통과한 피드백만 분리된 데이터셋에 모은다.
3. 승인 예제가 충분히 쌓였을 때 주 1회 또는 필요할 때만 파인튜닝한다.
